# OpenChess 2.1

The desktop workspace uses a pale blue shell with persistent navigation. Click
OpenChess to return home. Small home windows rearrange the cards into two
columns; use the mouse wheel over the content to reach the history below.
Preferences contains language, background image, cover/contain and overlay
controls. Version 2.1.1 adds ten application themes and an independent dark-mode
switch; both persist between launches. Board and piece themes remain independent. The bundled Noto Sans CJK
font supplies Chinese glyphs; its OFL license is in assets/fonts.

## Analysis

Learn → Analysis accepts PGN or FEN and provides saved analysis and position
setup. Position Setup supports a piece palette, drag/drop, right-click removal,
an eraser, undo/redo, side-to-move, castling rights and a complete editable FEN
(including en-passant target and both counters). Incomplete positions can be
edited; Load validates them before starting analysis. Game tags are editable.
Saved analysis preserves initial FEN, variations and the current browsing node.
Opening another analysis does not change a canceled setup. Analyses belong to
the current account or offline profile and are stored locally.

## Practice and daily archive

Ordinary practice uses Around my rating with five relative difficulty options:
Very Easy (-600), Easy (-300), Normal (0), Hard (+300), Very Hard (+600).
Each option targets the current rating plus its offset, within -150/+149.
If that range is unavailable, selection uses the closest available rating,
retaining the requested theme when possible. Rated settlement uses actual
puzzle rating and expected success: harder puzzles earn more and lose less.
Smart practice adjusts difficulty automatically.

The 6,000 bundled Lichess CC0 puzzles cover ratings 600–2799. Every bundled
solution is checked by the shared move generator in test_workspace. Imports
continue to extend this pool. Smart practice explores initially, then selects
weak themes (70%), less-practiced themes (20%) and errors older than a day
(10%). Statistics use the first result for each ordinary puzzle, within the
last 30 days, with at most 50 observations per theme and smoothed accuracy.
Hints count against independent success; elapsed time breaks accuracy ties.
Selection prefers rating ±200, expands to ±400 and then falls back to the pool.
Review puzzles do not earn or lose rating a second time.

The pills beneath the board belong only to the current process/account.
Click one to review without rating changes or new training observations.
The current unfinished question is retained, and time spent reviewing or on
another page does not count as answering time. Rated results are displayed
only after server settlement when signed in. An incorrect answer or reveal
settles a rated attempt once; a successful hinted answer earns no points.
Unrated attempts never change rating. Repeating a previously settled puzzle
cannot farm rating, even through a new attempt identifier.

Daily puzzles are always unrated. The calendar uses Monday-first weeks and
allows any published past date, including dates before account registration.
Future and unpublished dates are disabled. The server starts its permanent
archive on first activation and backfills missed dates on restart. The day
boundary is midnight Asia/Shanghai (UTC+8), independent of server timezone.
Monday–Sunday rating bands are 600–799, 800–999, 1000–1199, 1200–1399,
1400–1599, 1600–1899 and 1900–2399. Each date stores an immutable full snapshot.
Updating the puzzle pool cannot replace previously published puzzles.

Hints are allowed for completion. Revealing the solution marks that attempt
as practiced, without completing the day; start a fresh attempt to complete it
later. Completing old dates fills gaps and recalculates both streaks. The
current streak ends today, or yesterday if today is unfinished. Daily attempts
never enter ordinary smart-training statistics or create rating events.
Offline profiles maintain a separate archive. A signed-in account without a
connection can review cached official puzzles; uncached dates need a connection.

## Online services

Keep the existing account database when upgrading. SQLite migrations are
repeatable and retain users, password hashes, tokens and legacy ratings. The
four chess categories inherit the legacy ELO on migration and then change
independently. Bullet/Blitz/Rapid/Classical use base + 40 × increment with
boundaries 180/480/1500 seconds. No historical ratings are fabricated; the
initial migration event marks the starting point of the new graph.

Connections, heartbeats and clocks continue when returning home. A Return to
game control shows the current clocks. Another board cannot replace a live
online game. The server also prevents an account from joining another game or
queue through a second connection. Matchmaking separates base time, increment
and rated mode. Challenge invitations support time, increment, color and rated
mode and expire in 60 seconds. Friends support requests, acceptance, deletion,
blocking, private message history, offline delivery and read state. Blocking
prevents new messages and invitations. Completed games, ratings, lifetime
head-to-head scores and rematch-series scores persist in SQLite. Rematches
retain the series and swap colors after mutual acceptance.

Run the server with the existing OPENCHESS_ACCOUNTS_DB path. The puzzle pool
can be overridden by OPENCHESS_PUZZLES; otherwise assets/puzzles/starter.jsonl
is used. Back up the database together with its WAL files while running, or
stop the server before copying it. Deployment of the upgraded server remains
necessary for these services; the application cannot upgrade a remote server.

## Protocol v3

The existing typed messages remain, with HELLO v=3. A client sends:

```json
{"type":"request","request_id":1,"op":"daily.get","day":20742}
```

Responses contain type=response, op, request_id, ok and either data or error.
The runtime adds actor to identify the authenticated account. Account-scoped
requests derive identity from the connection, never from a supplied owner.
WebSocket fragments are reassembled before parsing; oversize messages are
rejected. A successful puzzle submission is idempotent by account and attempt.
The legacy client-claimed puzzle_result is rejected.

| Operations | Main arguments / returned data |
| --- | --- |
| profile.get / profile.set | nickname, avatar, five current ratings |
| ratings.history | category 0–4, since epoch seconds; daily or monthly points |
| people / friends / blocks | search, offset; paginated players and notification counts |
| friend.action | peer, action=request/accept/decline/remove/block/unblock |
| messages / message.send / message.read | peer, offset cursor, text, through message id |
| challenge.create / list / accept / decline / cancel | peer, time and inc in ms, color, rated, id |
| games / game.get / headtohead | offset, id, peer; PGN, lifetime and series scores |
| puzzle.next | smart, rated, optional day; immutable puzzle and attempt id |
| puzzle.submit | attempt, complete UCI line, hint, reveal, elapsed ms |
| daily.get | optional day (epoch day in UTC+8); snapshot |
| daily.calendar | first, last epoch days (maximum 366); published days and progress |

The daily calendar returns current/longest streaks with completion state. It
is also the streak query; no separate call is needed. Public archive reads
work without login, whereas personal progress and ordinary training require
authentication. Requesting rated=true for a daily puzzle is ignored by the
server. Solutions and legal moves are validated using the stored snapshot.

## Build validation

SQLite is now required for desktop storage as well as server accounts. Run
make test for rules, puzzle data, persistence, social permissions, network
integration and UI regression checks. test_ui21 uses SDL's software renderer
and writes inspection images under /tmp. The Windows workflow supports
publish=false to build and retain a verified ZIP without modifying a Release.
The existing Stockfish discovery and automatic installation paths remain.
